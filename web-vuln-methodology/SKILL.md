# Web 漏洞挖掘方法论

一套「可证伪」的漏洞挖掘流程。核心思想：**每一个动作都是可检验的假设，没有预测就不发包。**

## 0. 授权与伦理（第一步，不可跳过）

- 只测**你已获得书面授权**的目标，或**平台规则明确覆盖**的范围。
- 禁止：未授权探测、获取/维持 shell、植入后门、拖库、破坏数据、横向移动。
- 验证影响用**只读探针 + 最小影响证据**（`id`/`whoami` 单次回显），不落持久化。
- 没有授权时，只在本地靶场（Vulhub、DVWA、自建 lab）练习。

## 1. 侦察与攻击面入账

1. **资产测绘**：子域、IP、端口、指纹（Wappalyzer/httpx/nuclei -tech）、历史存档。
2. **入口发现**：登录/注册/搜索/上传/API/管理面板/静态文件。
3. **攻击面入账**：把每个输入点记进台账（参数、header、cookie、上传、认证流程、接口），每项标注：方法、参数、认证态、响应形态、来源。
   - 从 JS 里挖出的接口是「发现」，不是「漏洞」。

## 2. 立假设 + 预测

对台账里每一项，先写下一句可证伪的预测：

- 「若 `id` 拼进 SQL，`1 AND 1=1` 与 `1 AND 1=2` 的响应应当不同。」
- 「若登录信任响应体，把 `success` 改 true 应能进后台。」

**没有预测就不发包。** 这是防止「盲扫 + 误报」的核心纪律。

## 3. 无害探针 → 后果证实

1. **先发基线**（正常合法请求），记录响应。
2. **再发篡改**（受控变体），记录响应。
3. **对照**：只有「基线 vs 篡改」出现稳定差异，才算有信号。
4. **后果证实**：升级到可证明影响的最小请求，留下 raw 请求 + 响应 + 副作用证据。

> 单次 403 / 空响应 / 超时 / 版本猜测都**不是**结论。扫描器命中 ≠ 漏洞。

## 4. 假阳性排除

每类漏洞都有典型误报（详见 `web-vuln-classes`）。排除时要能回答「为什么不是漏洞」，而不是「看起来不像」。

## 5. 组合升级

单点漏洞往往要拼成高危才有价值。常见链路：

```
信息泄露 → 认证绕过 → 后台上传 → RCE
SQLi     → 文件读写 → 写 webshell / 读凭据（仅靶场）
SSRF     → 云元数据 169.254.169.254 / 内网 → 接管
LFI      → 日志投毒 / /proc/self/environ → RCE
IDOR     → 账号接管
```

## 6. 证据规格

没有完整 raw 请求 + 响应片段（或命令副作用），不得声称「已确认」。

存放：`evidence/<target>-<bug>-{request,response,sideeffect}.txt`

## 7. 报告要点（决定能不能过审）

- **影响面**：能造成什么后果，落到业务语言（谁的数据、什么权限）。
- **复现步骤**：一步步可照做，含版本/前置条件。
- **修复建议**：升级版本 / 关闭功能 / 加校验 / 加 WAF 规则。
- **CVSS**：按实际影响打分，别虚高。

## 8. 全过程纪律

- 限速低噪声：单端点守住请求预算，遇到 403/429/503 立刻停。
- 不确定就标注「未确认」，不把「可能」写成「确认」。
- 破坏性/写入性验证：先确认授权，只在测试账号或临时对象上做，事后回滚复查。
